# ADR-003: 采用渐进式重构

## 状态
已采纳（2025）

## 背景
项目经历多次重构（Phase 1-7），每次都面临"是否推倒重写"的问题。大规模重写存在以下风险：
- 引入新的 Bug 难以追踪
- 功能回归范围过大
- 无法在中途交付价值

## 决策
所有架构改进必须采用**渐进式重构**。

## 核心原则
1. **一次只改一个关注点**：命令执行、设备管理、知识库各自独立演进
2. **每步可独立验证**：每次修改后必须运行全量测试
3. **保持兼容**：不删除原有接口，直到新接口稳定后再逐步废弃
4. **安全网先行**：任何重构前先建立分支、测试基线、文件哈希快照
5. **小步提交**：每次提交不超过 8-10 个核心文件

## 实践案例
- Phase 1: 先修 Bug（不改变架构）
- Phase 2: 提取核心模块为独立类（不改变接口）
- Phase 3: 工具直连 Python 模块（不删 Flask 路由，逐步移植）
- Phase 4-7: 逐步增强功能（Telnet 可靠性、KB 治理、项目清理）

## 后果
- 重构周期较长，但每一阶段都可交付
- 需要同时维护新旧两套代码过渡，增加临时复杂度
- 但避免了"推倒重来"导致的长时间不可用
